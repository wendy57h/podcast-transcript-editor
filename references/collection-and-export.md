# 播客从搜寻到阅读交付的 SOP

按需进入相应阶段：只导出现成合集时，从“当前版本快照”开始；只做文字校对时，使用 transcription.md；没有请求发布或更新飞书时，不把文件制作扩大为线上内容改写。

## 来源发现与选集

只有播客链接或节目名、尚未取得完整材料时，先读 [source-discovery.md](source-discovery.md)，完成音频/文字搜寻与覆盖核验，再进入编辑。以下是选集层面的记录和排序规则。

1. 从用户给定的单期链接、标题、多期清单、全栏目、嘉宾、主题或时间建立候选；缺失范围与格式时按 `SKILL.md` 简短引导。用官方主页、小宇宙本期页面、RSS、官方视频及 shownotes 核对单集身份，再优先寻找已有精校完整稿或完整转录稿，官方文章作补充。搜索命中先确认是不是同一期完整节目，避免只凭嘉宾名字认定。全栏目任务处理目录分页、按单集 ID/GUID 去重，并记录检索截止时间和未覆盖目录。
2. 给每期记录节目名、原始期号、嘉宾与主持人、发布日期、时长、原始链接、可得材料类型和覆盖范围；缺失字段留空，不猜。多人节目保留联合主持人及现场发言者，不能强行归到一个人。
3. 区分音视频全文、字幕、逐字稿、主题精读、宣传节选和摘要；只有摘要时，不能扩写成声称来自原节目的完整对话。
4. 优先复用已取得、可追溯的源材料。页面字段、音频 URL、下载方式会变化，核对当前返回；失败时返回来源更新，不把历史接口当成永久协议。
5. 合集排序按用户偏好决定。同主持人集中、节目内部按原顺序、访谈主题递进是可选策略；不能为了主题重新排列单篇内部问答。保留原节目 EP 编号，将阅读序号单独管理。

## 转写、校对与定稿

操作细节见 [transcription.md](transcription.md)。关键产出是可回溯的段落记录，而不是只剩一份润色后的长字符串。

- 保存原始音频/字幕/文字材料，编辑稿独立存放。每段可带 speaker、role、原文、编辑文、源片段及真实时间依据。
- 先核对说话人和录音顺序，再清理语气词、无意义口吃、确定重复与广告；保留例子、数值、条件、否定和追问关系。
- 名字、机构、技术术语用官方来源与上下文修正；不要用全局同音或子串替换。短句重复、问号和时间回退只能提示疑点，不能自动决定角色或删除内容。
- 开头、结尾、每个换章点和角色变换处需要核对。乱码、重大数字和错听优先截取前后完整问答，结合原音频重新判断。确实不明就保留疑点，不能编一个更顺的句子。
- 嘉宾核心洞察与全文分开概括，保留前提和边界；简介附真实原节目链接。时间戳必须有原音频、字幕或官方章节依据。
- 保存实际检查范围，例如“全文文字校对＋19处片段重新转写和上下文比对”；不能据此声称整段原音频已全部回听。

## 飞书输出与当前版本快照

飞书命令、身份和写入验收见 [feishu.md](feishu.md)。只处理用户指定的对象；已经有明确授权的原位更新继续执行，不重复索要同一授权。

- 已有文档记录 Wiki 节点、实际 Docx token、父节点、标题和 revision。默认原位修改，保留链接和原有资源，不另建独立文档冒充原文已更新。
- 常用正文为“开篇简介／嘉宾核心洞察／全文文本”，全文下以主题章节保留时间顺序；默认可用主持人全段蓝色加粗、嘉宾普通文字。用户当前样式始终优先。
- 写入前 XML 预检；修改时用最新 revision 与合法块 ID；写入后回读，逐块比对内容、样式、资源、标题和目录归属。部分成功或响应不明时先查实际状态，避免重复写入。
- 导出从线上重新读取，而不是取前次本地稿。完整快照应包含正文 XML、样式、引用/资源信息及版本；合集目录顺序以当前页面为准，不以旧清单或标题排序推断。
- 若检测到导出期间有源文档更新，读取变化部分并更新产物，或如实记录使用的快照时间；不要静默盖过用户新改内容。
- Wiki 侧栏排序与正文阅读目录是两个不同目标。查询实际支持能力；不能把“正文链接已重排”说成“侧栏已重排”。

## 导读与统一源数据

只生成用户选择的格式；使用一份定稿源数据生成所选产物，避免 PDF、TXT、EPUB 的内容各自漂移。选择本地文件不要求先写入飞书，未选择 EPUB 时不因有对应章节就自动多做一份。

建议清单包含每篇的目标 token、标题、原节目链接、排序、源 revision、角色标签和章节结构；生成记录还需有文件名、SHA-256、检查结果和未解决疑点。字段按任务需要设置，不要求为未知值编造内容。

导读说明整辑的共同问题和阅读顺序，每篇用自然段融合阅读线索、前后关联与思考问题。可将阅读线索与思考问题融合成自然段；用户另有偏好时遵循其要求。导读是编者文字，不能伪装成嘉宾引语。

## PDF：适合长文阅读的排版

### 生成

- 根据设备和阅读场景选页幅。已使用过 180×255 mm、正文约10.5 pt、行距1.85、字距约0.035 em及18 mm侧边距；这是可复用起点，不是每份读物的固定要求。
- 已验证的风格是思源宋体正文、清晰标题字体、蓝色主持人发言与有限的主题色；字号、留白和对比度比装饰更重要。字体需要实际存在、可嵌入并覆盖使用的字符。
- PDF 的洞察区单独设计，不必照搬飞书 callout。淡紫底独立卡片、柔和编号、时间提示和充足留白可作为起点；每条尽量完整跨页，不把整个很长的洞察列表锁成一页。
- 可从当前 XML 转 HTML/CSS 后用本机浏览器打印。遇到不认识的资源不能默默丢弃；下载/转换资源或明确处理其用途。
- 等待字体、图片和整篇内容加载完成，开启打印背景，检查纸张与页边距。CDP 输出很大时可用流读取，避免把整份 PDF 的 base64 打到工具输出。
- 浏览器打印不一定真的生成书签，即使请求了 document outline 也要查结果。必要时保留内部链接，再补写分层书签；每次重新排版后重新计算书签页码，不能复用旧版页码。
- 浏览器复用残留的 DevToolsActivePort 可能连接到已退出进程；每次导出使用独立临时 profile，勿读取真实用户浏览器配置或凭据。

### 验收

- 检查页数、空白页、正文裁切、卡片跨页、行距及目录和书签跳转。至少渲染封面、目录、导读、第一篇开头、洞察跨页、长文中部和末页；仅看 HTML 不算检查 PDF。
- 从实际 PDF 提取文本，与源段落按顺序比较。排版出现换行或页脚插入时，先明确剔除已知页脚并规范空白，不能把正文差异当排版忽略。
- CJK 字体提取出的兼容字符可用 NFKC 辅助比较；出现异常字形、非字符或连字符差异时，先查看源文、PDF画面与提取结果，不能用宽松替换掩盖缺字。
- 绝对定位的卡片编号曾使视觉顺序与 PDF 文本提取顺序不一致；改用正常文档流布局后重验。画面好看不代表复制/检索顺序正确。
- 如检查字体嵌入，需要递归进入 Type0 的 DescendantFonts / FontDescriptor；不能因只看顶层 BaseFont 得到空值就判中文字体不存在。
- PDF 导出后的页数与文字量都受排版影响，不能以页数相近代替完整性检查。

## TXT：主章清楚，章内标题不过度升级

TXT 是纯文本，不含明确的父子目录数据。阅读器会自行识别分章；本工作流不依赖微信读书某一版本的精确识别规则，因此区分“源文件设置的章节标记”与“客户端实际识别的章节”。

1. 先确定真正的主章。此类选集适合“导读一章＋每篇完整访谈一章”，例如2篇访谈加1篇导读，即3个主章；不把每个话题、简介或洞察都写成连续主章。
2. 主章标题独占一行，例如 `第2章 示例嘉宾：把一个想法做成产品｜示例播客 EP.1`，章间留清晰空行。
3. 章内可用 `〔嘉宾核心洞察〕`、`〔话题：01:20｜示例话题〕` 等普通文本提示。不要以为 `第X节`、缩进或 Markdown `##` 就能保证微信读书建立二级目录。
4. 保留说话人名称、问答段落、来源链接和实质疑点；去掉 HTML/XML 标签、纯装饰符号和只适用于 PDF 的页码。
5. 可使用 UTF-8（可带 BOM）及 CRLF；这只是编码与换行选择，不控制目录层级。
6. 本地检查主章标记数量及顺序、正文全文和段落覆盖，确认没有旧版“第X章”残留。没有真正导入目标 App 时，不能说“微信读书已按预期识别章节”。

曾遇到的失败模式：把每篇简介和内部话题全部升级为主章，造成大量同级章节。修复是只给导读和每篇访谈设置主章，将内部话题留在所属访谈内；仅把“章”替换成“节”不能保证修复。

## EPUB：需要父子目录时明确编码

当用户希望同时有“每篇访谈”的主目录和可跳转的内部话题，EPUB 能明确保存层级，避免仅靠 TXT 标题启发式。用户只要 TXT 时仍提供 TXT；可说明 EPUB 的作用并在适当情况下补充，不强制更换其指定格式。

- EPUB 3 的 nav.xhtml 使用嵌套 ol/li，父条目链接到访谈起点，子条目链接到该访谈内部主题的 fragment ID。目录顺序与正文 spine 一致；同一主题不能被误列为另一篇访谈。
- 可同时提供层级一致的 NCX 兼容导航。例如3个一级条目与其下若干话题入口；导航节点总数与同级章节数量是两回事。
- 每篇保留完整简介、洞察和对话；章节锚点、内部链接、资源路径与样式都要可解析。自适应排版通常不必嵌入大字体，允许阅读器选择字体和字号。
- mimetype 应在 ZIP 首条且不压缩，内容为 application/epub+zip；container.xml 指向有效 OPF；manifest、spine、唯一标识、语言与修改时间完整。
- 先用 XML/ZIP 检查链接、锚点、清单、顺序及全文，再用 EPUBCheck 做正式包校验。EPUBCheck 零错误不是目标 App 导入实测，也不保证每个客户端会怎样显示目录。

目录层级规范：[W3C EPUB 3.3 导航](https://www.w3.org/TR/epub-33/#sec-nav-ol)。校验工具来源：[W3C EPUBCheck](https://github.com/w3c/epubcheck)。根据当前官方发布获取合适版本，不将某个历史版本号作为永久要求。

## 交付与复用范围

- 给用户发送真实文件。飞书中按 im 技能使用 incoming message ID、机器人身份及相对文件路径回复；本地 Markdown 链接不能代替附件交付。
- 文件名区分版本，保留源快照与校验记录。修正用户已导入的书籍时，不擅自删除其旧书或批注。
- 最终简要说明改动、文件内容和实际验收范围。分别报告内容核对、视觉抽查、包格式校验及客户端实测，避免笼统地说“全部验证”。

## 可移植性与参考实现

本仓库包含工作流、参考说明和版式检查器，不包含旧任务的文档清单、源快照或机器专属导出脚本。使用当前环境中已有的文档工具、ASR 和 PDF/EPUB 工具完成对应阶段，并重新验收。示例与截图使用仓库自写的演示内容，不代表真实播客引语。
